Deep Dive · Healthcare & Cost Architecture Engagement

Modernizing legacy clinical systems and cutting structural cost

An on-premise clinical platform — collecting and routing patient biometric data from connected medical devices to care teams — had hit the scaling and reliability limits of running as a single monolith on fixed hardware. This is how I decomposed it into managed, containerized services and brought the same cost discipline to several other engagements alongside it.

The problem

A monolith that couldn't scale with the data it was collecting

The platform ingests a continuous stream of biometric telemetry — vitals like blood pressure, pulse, glucose, and oxygen saturation — from thousands of connected patient devices, and routes it to clinical teams for real-time monitoring and historical trend review. It had been built and run as a single on-premise application, and that design was showing its limits in three specific ways:

  • Fixed hardware couldn't absorb device growth. Every new batch of connected devices meant provisioning more physical capacity ahead of time, whether or not it was needed yet.
  • Reporting queries competed with live ingestion. Clinical dashboards querying historical vitals ran against the same database handling real-time device writes, so heavy report load could visibly slow down live data ingestion.
  • Deployment and disaster recovery were manual. Shipping a change or recovering from a failure both depended on a person following a runbook by hand, which put a ceiling on how fast either could happen.
Architecture

Decomposing the monolith into managed, independently-scaled services

I re-architected the application as a set of containerized microservices running on managed Kubernetes, with a deliberate split between the two things clinical software actually does: handling live device and portal traffic, and running analytics on the history of that data.

Multiple independent application APIs share one load balancer instead of provisioning one per service — a small decision that has a real cost effect once you're running more than a handful of services, covered in the outcome below.

Reducing database load

Taking reporting traffic off the live database entirely

Rather than scaling the operational database up to absorb both live writes and heavy analytical reads, I decoupled the two: vitals stream out of the application tier into a purpose-built real-time analytics pipeline, and clinical dashboards query that pipeline instead of the production database.

The caching layer's role: session state and frequently-read reference data sit in an in-memory cache in front of the operational database, so routine application reads don't round-trip to disk at all. Combined with moving analytical reads onto the streaming pipeline, direct database read load dropped by roughly half.
Cost-aware compute

Applying the same discipline across several engagements

This pattern — right-sizing compute instead of running static, always-on fleets — wasn't unique to one platform. Across several client engagements during the same period, I applied a consistent set of cost levers:

LeverWhat it replaced
1Dynamic, right-sized compute in place of statically-provisioned server fleets sized for peak load year-round.
2Shared load balancers across grouped services instead of one dedicated load balancer per microservice.
3Graviton-compatible node pools where workloads allowed it, alongside legacy-compatible nodes for what couldn't move yet.
4Automated deployment and disaster-recovery pipelines in place of manual, runbook-driven processes.

None of these are exotic individually — the value was in applying all of them consistently, with actual financial modeling behind each recommendation rather than a generic "move to cloud-native" pitch.
