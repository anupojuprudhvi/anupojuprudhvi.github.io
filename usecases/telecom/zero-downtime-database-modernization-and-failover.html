Modernizing a secure telecom platform without downtime

A secure mobile-communications platform used by financial institutions and healthcare organizations, handling large volumes of sensitive call and message data every day. It ran on a legacy on-premise database with manual, hardware-dependent failover and no room for an extended maintenance window. This is how I moved it to the cloud without breaking any of that.

The problem

Three constraints that couldn't be traded off against each other

The platform's database had been running the same major version for years in an on-premise datacenter, and every part of the stack around it had grown to depend on that fact. Three specific constraints made a normal "lift and shift" impossible:

  • The database was eight-plus major versions behind current. Bridging that gap meant not just a version upgrade but a full rewrite of legacy triggers, deprecated data types, and C-level extension code — while the platform kept taking live traffic.
  • Failover was manual and hardware-dependent. High availability relied on an on-premise clustering setup with a node-fencing script tied to physical server power control. When a node failed, recovery meant a human being paged in, not an automated response measured in seconds.
  • The telecom software was licensed to physical hardware. The call-processing and messaging engines had licenses bound to a network interface's MAC address and static IP. A standard cloud autoscaling event — where a replacement instance gets a new virtual network interface — would silently invalidate the license and take the service down.

Any one of these would be a normal migration problem. Solving all three at once, with a platform that financial and healthcare customers depend on for real-time communications, is what made this engagement different.

Architecture

Splitting stateful and stateless workloads onto purpose-built node types

Rather than treating every EC2 instance the same way, I separated the platform into two node roles, each with its own provisioning pipeline and its own failover story — connected through one networking hub, with a mirrored standby in a second region for disaster recovery.

Why split them at all: the application nodes are disposable — replace one and nothing is lost. The database nodes are not, and that's exactly where the licensing constraint and the failover constraint both live. Keeping that distinction explicit in the infrastructure, rather than treating every instance identically, is what made a purpose-built failover path possible in the first place.
Database modernization

Bridging an 8+ major-version gap without a maintenance window

The database side of the platform is four separate logical databases: core accounts and billing, an asynchronous task queue, SMS/MMS messaging, and call detail records (CDR). All four needed to move from the legacy engine to a modern Aurora PostgreSQL cluster together, without a multi-hour cutover window the business couldn't afford.

The migration ran on AWS Database Migration Service using change-data-capture replication, so the target database stayed continuously in sync with live production traffic while the schema and application code were modernized underneath it:

Schema & syntax modernization

Extracted the legacy schema, rewrote deprecated triggers and geometric types, and recompiled C-level extension code against the modern engine's internal APIs.

Baseline full-load migration

DMS performed an initial bulk load of all four databases over an encrypted VPN tunnel while the legacy system kept serving live traffic.

Continuous CDC replication

Ongoing transactions streamed to the new cluster in near real time, keeping replication lag effectively at zero for the full migration window.

Automated validation

Scripted checks compared row counts, checksums, and index integrity between the legacy and Aurora databases before cutover was even scheduled.

Final cutover

Paused write traffic briefly, let DMS apply the last transactions, verified sequence alignment, and redirected the application layer to the new cluster through local connection pooling.

Every database connection now routes through a local pooling layer on the database node itself rather than opening a raw connection per request — the difference between a few hundred pooled connections and the connection exhaustion that direct-to-database access at this scale would otherwise cause.

High availability

Replacing a 37-line fencing script with a sub-60-second automated failover engine

The original high-availability design was a Linux clustering setup using a fencing script: if a node looked unresponsive, the script would cut its power and hope nothing else was wrong. It had no application-level health checks, no protection against two nodes both believing they were primary at once, and it had no concept of the licensing constraint at all.

I replaced it with a serverless failover engine that runs the entire recovery sequence — including the parts a hardware fencing script structurally can't do, like carrying the license-pinned network interface across to the new primary.

Licensing continuity

Making the cloud look like fixed hardware to a license that can't tell the difference

The call-processing and messaging software licenses are node-locked to a MAC address and a static private IP — a normal assumption for on-premise hardware, and a direct conflict with how cloud autoscaling and failover normally work. The fix was to stop treating the database node's identity as tied to the instance at all, and pin it to a portable resource instead.

Primary network interface
Handles OS management, SSM access, and monitoring. Freely replaceable — the license never looks at it.
+
Secondary, license-pinned interface
A dedicated elastic network interface with a fixed MAC address and static IP, detached from the failed instance and reattached to the standby during failover. 
resource "aws_network_interface" "license_pinned_vip" {
  subnet_id       = var.private_db_subnet_id
  private_ips     = [var.vip_private_ip]
  security_groups = [aws_security_group.db_persistent.id]
  description     = "License-pinned VIP interface, carried across failover"
  # tagged so the failover engine's IAM role can attach/detach
  # this interface and nothing else
}

During failover, the engine detaches this interface from the failed node and reattaches it to the promoted standby. The application reads back the identical MAC address and IP it started with, so it boots without triggering a licensing fault — zero manual re-licensing, and zero downtime attributable to software licensing across the entire migration.

Data protection

Field-level encryption the database itself never sees through

Disk-level encryption protects against physical theft, but not against a compromised query path reading plaintext rows directly. Given the sensitivity of the data — phone numbers, message content, and subscriber identity across call and messaging records — that gap wasn't acceptable, so encryption happens before the data ever reaches the database.

  • 13 distinct fields across call, SMS/MMS, and directory records are encrypted at the application layer using AES-256-CBC with a unique initialization vector per value.
  • A lightweight local key service on each node keeps encryption keys in memory rather than in application code or config files, and supports online key rotation without re-encrypting historical data.
  • PostgreSQL-side functions handle the encryption and decryption calls natively, so both the legacy C-based engines and the modern services could adopt it without a parallel code path.
Validated, not assumed: automated compliance scans of full database exports searched for unencrypted phone numbers and message content across the entire dataset. Zero plaintext matches — the standard the SOC2 and GDPR audit process required.
Storage

Retiring a single point of failure, and cutting cold-storage cost with it

Call recordings, message attachments, and application configuration lived on a single on-premise file server — a hardware failure there took down every dependent service at once. I migrated that to a Multi-AZ Elastic File System, replicated by AWS DataSync with end-to-end checksum verification so a multi-terabyte transfer completed with zero file corruption.
